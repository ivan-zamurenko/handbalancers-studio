# Handbalancer’s Studio — рабочий контракт агента

## Задача
Строй новый код в корне этого проекта по одной карточке roadmap/tasks за раз. Последнее указание владельца: не создавать вложенный execution-v4 или отдельный рабочий проект. Это greenfield, не миграция старого runtime. Клиент и админка — один продукт и общая БД. Существующая Git-история сохраняется, origin этого проекта используется для рабочей ветки task/execution-v4. Старый runtime и managed Auth не использовать и не восстанавливать.

## Старт одной задачи
Прочитай `.workflow/CURRENT.md`, `docs/decisions.md` при начале сессии и карточку выбранной задачи. Найди следующую через `python tools/roadmap.py next`. Открой только релевантный контракт из `docs/`, исходники затрагиваемого модуля и узкий diff. Не перечитывай весь handoff при каждой правке.

## Разработка
Поведение: сначала выполнимый тест из сценария карточки, затем наблюдаемый RED по ожидаемой причине, потом минимальная реализация и GREEN. Документация/tooling проверяется подходящим validator, не фиктивным assert True. Исправление ошибочного теста требует записанной причины и проверки против требования; не ослабляй ожидание ради зелёного результата. Не меняй контракт молча.

Одна карточка — один основной green commit с тестами и реализацией. Сначала узкие тесты, затем affected-module suite. Полный suite — на PR/этапе, а не пять раз на неизменённом коде. CI green не означает реальный OAuth/Stripe/AI. Без стенда статус env_blocked, не passed. Не пропускай падающий тест, не используй broad mocks вместо DB/RLS/concurrency.

## Границы
FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL/Supabase Auth + Jinja/HTML/CSS/vanilla JS. Не вводи React, микросервисы, ORM repository hierarchy, внешнюю очередь или новые provider integrations без измеренной необходимости/записанного решения. Новый SQL создаётся перед первой использующей его командой, не весь будущий словарь сразу.

HTTP routes тонкие; authorization и transaction orchestration в module service. Domain policy не зависит от Request/Stripe/Supabase SDK. Одна product command — одна транзакция; внешняя сеть не внутри длительных DB locks. У completed snapshots и published trees отдельная защита от изменения.

Проверяй owner цепочку, актуальный entitlement и row/context revision на сервере. User metadata/URL/body/AI output не источник роли. Private notes не client feedback. AI не исполняет SQL и не меняет прошлое. Фактические секреты и private videos не печатай, не коммить и не отправляй провайдерам.

## Автономность
Разрешены безопасные локальные изменения, тесты, рефакторинг внутри карточки и коммит по карточке. Не спрашивай «продолжать?» после каждого green. Продолжай в пределах порученного диапазона; оставляй checkpoint на границе карточки. Если блокер касается только внешнего сервиса, запиши gate один раз и выполняй независимые ready задачи.

Нельзя без отдельного разрешения: удалять старую работу/production данные, force push, merge в защищённый main, делать live charges/deploy, покупать сервис, публиковать private videos или отправлять их AI. Разрешённый push идёт только в подтверждённый task branch remote. Не настраивай origin по историческому URL автоматически.

## Коммиты и handoff
Перед commit: git status, узкий staged diff, проверки карточки, отсутствие секретов. Не использовать git add . на непроверенном дереве. Commit subject указан в карточке. Push после green/review в разрешённую feature branch; отсутствие credentials фиксируй как push_pending.

Обнови `.workflow/CURRENT.md`, состояние задачи и `.workflow/evidence/<TASK>.json`: сценарий, RED/GREEN команды/результаты, непроверенное и следующий шаг. В отчёте укажи фактический commit SHA после коммита; не пытайся записать SHA коммита внутрь самого этого коммита.

## Агентская работа
По умолчанию один writer и один read-only reviewer. Делегируй только независимую ограниченную задачу с заданными файлами/контрактом/результатом. Shared migrations, root locks и state редактирует один integrator. Не создавай скрытых цепочек субагентов. Skill `.agents/skills/studio-task-delivery` используй для выполнения карточки; другие skills только по конкретному действию и после проверки происхождения/инструкций.

## Code review rules
Флагировать изменение источника истины, обход владельца/paid guard, потерю history, неверный RED evidence, ослабление тестов, неограниченный retry/external call, runtime fake tier, необработанную гонку и усложнение вне карточки. Форматирование оставить CI. Ошибки описывать с путём/строкой/сценарием воспроизведения, не общими замечаниями.
