# Как владельцу разрабатывать продукт с агентами

## Рабочая модель
Один Product/Integrator context хранит принятые решения, порядок задач и review. Один implementation agent выполняет карточку в checkout/worktree. Отдельный reviewer получает acceptance и diff и ищет дефекты. На старте достаточно writer+reviewer; второй writer только для реально независимых файлов после фиксации контракта.

Репозиторий и docs — память проекта. Чат не единственный источник состояния. Не копировать сюда credentials или private клиентские видео; всё секретное вводится в предназначенные панели/локальный secret environment.

## Новый контекст
Рекомендация для этого проекта: один implementation чат на одну карточку; можно 2–3 небольшие связанные карточки одного модуля. Новый чат после завершённого контракта/PR, перехода к другому модулю, существенной смены требований или повторного хождения по кругу. Это практическая схема, не официальное ограничение OpenAI и не правило «каждые 20 сообщений».

Не сбрасывать контекст посреди незаписанного RED/гонки/миграции. Сначала checkpoint: task ID, branch, base/current SHA, что меняли, точная команда/ошибка, какие гипотезы уже проверены и next action. Если принудительно закончить пришлось до green, отметить WIP и не мержить как готовое. Сохранить diff локально или отдельный явный WIP branch по политике; не объявлять завершённым.

На каждом новом чате дать root/branch/task ID и попросить выполнить `python tools/roadmap.py context <ID>`. Агент читает CURRENT/card/нужный spec/diff, а не весь архив истории. Не просить «прочитай всё, пойми и начни» — это заставляет повторно исследовать уже решённое.

## Роли и распределение
Integrator один владеет `.workflow/state.json`, shared root configs/locks и порядком Alembic. Backend writer отвечает за schema/service/contract своей карточки. Frontend writer допускается параллельно только после согласованного API schema и на другом task, без править backend contract «для удобства». Reviewer по умолчанию read-only; report содержит severity, path/line, reproduction и требование, которое нарушено. Отсутствие замечаний — не доказательство реальной интеграции.

Браузерные/DB tests параллельных writers используют отдельные project IDs/ports/volumes. Не два агента в одной папке с общим dirty tree. Git worktree решает разделение файлов, но не автоматически изолирует БД/порты/секреты [S-WORKTREE].

Примеры независимой работы: implementer пишет signup, reviewer сверяет auth threat cases; backend исправляет typed DTO, read-only агент проверяет UA/EN copy; writer делает planner, reviewer разбирает race diff. Нельзя параллелить: два автора Alembic baseline, два менять same service/lockfile, frontend угадывает ещё не утверждённый payload.

## Сколько reasoning и агентов
Основной high profile для продуманной последовательной работы; max profile для auth security, миграций, concurrency, сложного planner review. Это выбранная стратегия качества, не обещание максимальной скорости. Для тривиального copy/style допустимо уменьшить effort по фактическому результату. Не включать fast/ultrafast billing автоматически: latency, стоимость и data residency — разные параметры [S-MODEL,S-CONFIG].

Ограничение starter-конфига — один subagent thread помимо primary. Обычно нужен один reviewer; не создавать дополнительных агентов из обязанности. Не раздавать одной большой задаче пять агентов, которые одновременно меняют те же таблицы. Субагенты полезны для ограниченного read-heavy анализа и возвращают короткие доказуемые результаты [S-SUBAGENTS].

## Что проверять тебе после задачи
Открыть локальный экран/получить воспроизводимый API сценарий; увидеть что именно добавлено; посмотреть diff и результаты тестов; убедиться, что нет «теперь перепишем весь проект»; принять или дать конкретный дефект. Тесты бизнес-правил проверяй особенно внимательно: зелёный тест на неверное требование даёт неверный продукт.

## Что от тебя действительно потребуется
Один раз настройка рабочего remote/локальных инструментов; отдельно credentials Supabase/Google/SMTP/Stripe (Apple не входить у поточний обсяг) в секретных местах. Позднее — методика/совместимость нагрузки, вариант видео, gold examples AI, реальные условия Pro+ и коммерции. Все эти пункты — `docs/owner-gates.md`. Их отсутствие не повод заново обсуждать C1/A1/C3 или прекращать независимую разработку.

## Три готовых сообщения
Начать: «Выполни S03-03 по карточке. Сначала воспроизведи RED, затем реализация и GREEN. Не меняй scope. Результат — проверяемый локальный commit и отчёт. Push только на подтверждённый task branch».
Проверить: «Проверь diff S03-03 против acceptance/auth-contract. Ищи нарушения ownership, enum/секреты, отсутствие meaningful tests и scope creep. Не редактируй код. Дай только воспроизводимые замечания».
Продолжить: «Прочитай CURRENT и карточку следующей ready задачи. Не повторяй архитектурное исследование; выполненные решения уже зафиксированы. При локальном blocker продолжи только независимо разрешённую работу».

Не проси агент «работай бесконечно до полного продукта». Задавай конечный диапазон (1–3 карточки) и разрешение на безопасные локальные действия; так остаются маленькие commits и контроль качества.
