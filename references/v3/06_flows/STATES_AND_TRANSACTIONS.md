# Data flow и состояния обеих сторон

## 1. Сквозной цикл
Упражнение → опубликованная ревизия → программа → опубликованное дерево → личный план/назначение → единый календарь → факт выполнения → отчёт → оценка/проверка → изменение будущего.
Дополнительное занятие входит в тот же календарь и сохраняет свой источник.
Проверка тренера и AI — разные авторы, но опираются на одни факты.

## 2. Состояния не сливаются в одно поле
| Объект | Состояния / измерение |
|---|---|
| Версия программы | draft → published; для изменения создать новый draft |
| Личный план | active ⇄ paused → archived; пустой active возможен до выбора основной |
| Основное назначение | pending → active ⇄ paused → completed/cancelled/superseded |
| Preview | ready/blocked → applied/expired/stale |
| Запрос изменения | pending → applied/rejected/cancelled/stale |
| Занятие календаря | planned → in_progress → completed; planned → skipped/missed/cancelled |
| Сессия | in_progress ⇄ paused → completed/abandoned |
| Полнота завершения | full / partial — отдельно от состояния сессии |
| Доставка данных | editing → saving → saved; saving → pending_sync/conflict/rejected |
| Проверка тренера | collecting → ready → in_review → published; ожидание evidence и needs_update отдельно |
| AI-задание | queued → access_check → quality_check → analyzing → succeeded; needs_input/failed/cancelled |
| Адаптация | draft → validated → applied; stale/rejected/needs_more_data |
| Готовность по оценке | ready / not_ready / needs_more_data — не состояние сети или AI-job |

Окончательные enum/переходы закрепить тестами. Успешный анализ не означает готовность клиента.
История прошедшего состояния хранится через записи/аудит, а не удаление результатов.

## 3. Публикация
Проверить полномочия и completeness → lock корневой version → validate дерево → freeze version и все дочерние цели → commit.
Нельзя менять дочернее упражнение в опубликованной программе обходом запрета на корневой строке.

## 4. Перепланирование Essential и админки
Выбор → preview по конкретному контексту → показ изменений → apply.
Apply блокирует/сверяет текущий plan, assignment и rules. Истёкший/устаревший контекст возвращает конфликт.
После успешной записи: одна ревизия плана, один набор изменений и один audit. Повтор команды возвращает прежний результат.
Начатое/завершённое не переносится.
Если разрешений клиента недостаточно, создаётся запрос; сам запрос не меняет календарь.
Одобрение тренером повторно считает/проверяет предложенный вариант по свежему контексту.

## 5. Дополнительное занятие
Дополнительное occurrence содержит личный plan_id и исходную опубликованную workout/version.
Оно не создаёт вторую основную программу.
Guided session наследует этот источник; наличие primary assignment_id для неё необязательно.
Факт допзанятия учитывается в дальнейшей проверке нагрузки. Прогресс этапов основной программы автоматически не увеличивается.

## 6. Start и запись
Start: авторизация, entitlement, источник, current state → одна session → snapshots → occurrence in_progress.
Стабильный idempotency key возвращает существующую session при повторе.
Set log: уникальность слота/стороны, owner, tracking_kind, expected revision; пропуск отдельным значением.
Параллельные устройства не перетирают друг друга молча.
Локальные pending записи разделять по пользователям; при logout не показывать чужие черновики.

## 7. Complete
Validate → сохранить финальные факты и время → session completed/full|partial → occurrence completed → новая версия фактового report → обновить контекст планирования → при контракте обновить review task → commit.
Отсутствие видео не блокирует Complete, но не создаёт отметку проверенной техники.
Нет повторного увеличения прогресса при повторе запроса.

## 8. Время и пропуски
Время активности хранится сегментами. Пауза исключается, отдых между подходами входит в занятие.
Длительное отсутствие в приложении не начисляется безусловно как тренировка; восстановление/исправление явно и аудируемо.
Пропуск «не было времени» отличается от «слишком сложно». Не выводить причину из одного количества посещений.
Новая неделя не удаляет историю. Пропущенные тренировки не становятся бесконечным долгом.

## 9. Видео и проверка
Один текущий ролик на session exercise; новая ссылка — новая версия.
Review/analysis ссылаются на точную просмотренную версию, не на изменяемый текущий URL.
Позднее evidence → needs_update → новая опубликованная версия review. Старый вывод не переписывается.
Private note не является client_summary.

## 10. Оценка и адаптация
Тестовая программа проходит через обычные sessions/set_logs.
Протокол связывает упражнения с критериями; оценка сохраняет evidence и версию методики.
Не измерено / не видно / не выполнено / не соответствует критерию — разные результаты.
Plus: AI proposal → domain validation → будущая персональная version → новые/заменённые будущие occurrence.
Pro: тренер принимает решение; AI не выдаётся за него.
При изменении плана в процессе анализа proposal stale. Во время активной сессии изменения, затрагивающие назначение, откладываются/требуют нового preview, а не меняют текущий workout.

## 11. Оплата и доступ
Checkout pending → verified external event → entitlement.
Repeat/out-of-order event обрабатывается идемпотентно. Redirect сам ничего не включает.
Переход тарифа меняет права будущих операций, а не авторство прошлых отчётов.
Неактивность не удаляет профиль и историю. Детали сохранённого доступа к платным материалам уточнить в договоре.
